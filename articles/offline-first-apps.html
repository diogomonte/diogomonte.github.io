Building Offline-First Mobile Apps That Actually Work

Sync conflicts, stale caches, and flaky networks — a practical guide.

Architecture Android
January 2025 · 8 min read

"Works offline" is one of those features that sounds simple until you implement it. Then you hit your first sync conflict at 2am and wonder why you ever left web dev.

The core principle: local is the source of truth

The most common mistake is treating the server as the source of truth and the local database as a cache. Flip it. Writes go to local storage first, immediately reflecting in the UI. Sync happens in the background.

Handling conflicts

Conflicts are inevitable when the same record is mutated on two devices while offline. The simplest strategy is "last write wins" using a updatedAt timestamp. For most apps, this is good enough.

For apps where data loss is unacceptable (note-taking, medical logs), use operational transforms or CRDTs — but that's a rabbit hole for another article.

Sync queues

Don't retry individual failed requests. Build a persistent sync queue. Every mutation is added to the queue; a background worker drains it when connectivity is available. On Android, WorkManager is your friend.

"A sync queue is a buffer between optimistic UI and eventual consistency."

Telling the user what's happening

Don't hide sync status. A small badge showing "3 changes pending sync" is far better than silent data loss. Users can handle "not synced yet" — they can't handle "where did my data go?"
