The System I Use to Actually Ship Side Projects

How I stopped collecting unfinished repos and started shipping.

Indie Dev
November 2024 · 5 min read

My GitHub used to be a graveyard of half-built apps. A Pomodoro timer with no timer. An expense tracker with no expenses. A recipe app with exactly one recipe (pasta).

Rule 1: Define "done" before you start

The most important thing I changed: I now write a one-paragraph definition of done before writing a single line of code. Not "a full-featured timer app" but "a timer that counts down 25 minutes and plays a sound when it hits zero."

Rule 2: Build the boring middle first

It's tempting to build the coolest features first — the animations, the onboarding flow, the settings screen. Build the core user journey first, all the way through, even if it's ugly. Polish is easy to add. Architecture is hard to change.

Rule 3: Ship an embarrassingly small v1

FocusFlow launched with one timer mode, no settings, and a light mode only. I was embarrassed by it. It got 200 downloads in the first week and useful feedback I never would have gotten from a feature spec.

"If you're not embarrassed by your v1, you launched too late."

Rule 4: Time-box ruthlessly

I give myself four weeks per side project. If it's not shippable in four weeks, the scope was wrong, not the timeline. Cut features, don't extend the deadline.
