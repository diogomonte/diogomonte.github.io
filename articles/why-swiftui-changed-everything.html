Why SwiftUI Changed How I Think About UI Code

The shift from imperative to declarative UI — and why it matters.

iOS SwiftUI
March 2025 · 6 min read

I spent four years writing UIKit before I wrote a single SwiftUI view. By that point I had formed strong opinions about how UI code should be structured — and SwiftUI challenged almost all of them.

The problem with imperative UI

In UIKit, you describe how your UI changes rather than what it looks like. You call tableView.reloadRows(at:with:). You manually update a label after a network response. You write viewWillAppear to set up state that should've been set when the view was created.

The result is UI state spread across dozens of lifecycle methods, delegate callbacks, and notification observers — all held together by convention and discipline.

"UIKit apps feel like managing a spreadsheet cell-by-cell. SwiftUI feels like writing a formula."

SwiftUI's model: declare, don't command

SwiftUI flips the script. Instead of telling the framework what to change, you describe what the UI should look like for any given state. The framework figures out the diff. 

struct ProfileView: View {
  @State private var isFollowing = false

  var body: some View {
    Button(isFollowing ? "Unfollow" : "Follow") {
      isFollowing.toggle()
    }
    .buttonStyle(.borderedProminent)
    .tint(isFollowing ? .gray : .blue)
  }
}

There's no explicit "update the button label" call. The view is a pure function of its state. When isFollowing changes, SwiftUI re-evaluates the body and updates the tree.

What took the longest to unlearn

The hardest habit to break was reaching for @State everywhere. Coming from UIKit, it feels natural to store everything locally. But SwiftUI rewards pushing state up and passing it down — the same thinking that makes React components composable.

Once I started thinking of views as functions rather than objects, the code got dramatically simpler. Smaller views, clearer responsibilities, and far fewer bugs from stale state.

The verdict after six months

SwiftUI isn't perfect — the lack of UIKit's fine-grained control still hurts in complex table views, and List performance can be frustrating. But for the 90% case, it lets me build better UIs faster with less code. I'm not going back.
